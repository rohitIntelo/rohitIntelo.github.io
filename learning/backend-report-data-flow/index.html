How a report becomes pixels

Tracing the backend read path that loads a report and fills its KPI cards and grids.

There is no single "report endpoint". Two quite different pipelines render what looks like one screen: a stateless query path for read-only report widgets, and a stateful, cached, replica-pinned path for editable planning grids. Nearly every confusing bug in this area comes from assuming a screen is using one when it is using the other.

01 · The shapeTwo paths, not one

Both start in the React app and both terminate in report-builder, a Python FastAPI service. What differs is everything in between.

Report widgetsPlanning grid
Endpoint /api/v1/widget-data /api/v1/plan/data
State Stateless — query, return, forget Warmed cache held on one replica
Query ibis expression via query-builder DuckDB over a materialised fact frame
Editable No Yes — /plan/edit, roll-down, write-back
Transport Request/response JSON JSON or SSE, chosen by Accept
A trap worth knowing. common/proto/widgetData.proto still defines a WidgetData gRPC service, and the gateway calls a method named fetchWidgetData. Neither is gRPC any more. report-builder/src/server.py states plainly that FastAPI "replaces the original gRPC server", and the gateway's client is a plain fetch() to ${REPORT_BUILDER_URL}/api/v1/widget-data. The proto is vestigial. Inter-service comms elsewhere in the repo are gRPC — this one is not.

02 · The hopBrowser → gateway → report-builder

The React app never talks to report-builder directly. Everything goes through web-gateway, an Express service that owns three things the Python service deliberately does not:

  • Authentication — Firebase auth resolves the caller.
  • Org scope — orgId is resolved from the authenticated request, never trusted from the query string. This is load-bearing: the only tenant-boundary P0 in this service's review history was one organisation's publication being loaded into another's cache.
  • Permissions — including agentScope, which opts report surfaces into per-agent narrow roles.

For planning routes the gateway is a genuine proxy (_proxyReportBuilder), not a client: it forwards the body, streams SSE back untouched, and preserves upstream status codes. Its abort budget is time-to-first-byte, which is why /plan/data gets 220 s while ordinary routes get 30 s — the endpoint legitimately sits silent while a cold cache warms.

03 · The sequenceWhat the FE actually calls

1. /report-config — the layout

Returns the report's widgets array: which KPI cards exist, which table widget exists, their columns, filters and view modes. This is layout and configuration only — no facts. Agent stream filters are injected into each widget's filter list here, with field names remapped against the widget's own column config, because the agent emits short names like product.class_nm while widget sources use their own.

2. /plan/{executionId}/state — the bootstrap

Plan-level metadata that used to ride on the config call: planStatus, planVersionId, editableMetrics, time periods, plus executionStatus and cacheWarmedAt. The FE polls this every 5 s while the execution is in flight and only fires /plan/data once it reports Completed. Splitting it out is what keeps the config response cacheable.

3. /plan/data — the numbers

One endpoint serves both the KPI tiles and the grid rows. It forks on the Accept header: text/event-stream gets SSE with progress events during a cold warm, anything else gets a single JSON body. A cold warm must emit progress — silence before the first event is indistinguishable from a hang.

04 · StorageWhere the numbers physically live

Four tiers, and a given request may touch all four.

TierHoldsRead by

The Databricks read has two executors behind one expression. lakehouse_layered builds an ibis predicate tree — plan-version and layer selection, grain excludes, fiscal-year window, node scope, seasons, channels — and then either hands it to the SQL warehouse or, by default, unbinds it onto a DuckDB backend that reads the Delta files directly. The design note on that change is worth internalising: 

There is no second implementation of any predicate, which is
the whole point: a hand-translated WHERE clause is exactly
where a "faster read" silently starts serving different numbers.

Same tree, different executor, one kill switch (MFP_DELTA_DIRECT=false). Everything after the scan — layer-overlap collapse, the long→wide pivot, rate derivation — is identical on both paths.

05 · AffinityWhy your request is pinned to one replica

The warmed frame lives in a DuckDB connection inside one container's memory. A second request that lands on a different replica finds nothing and warms again from scratch — expensive, and for an in-progress edit, wrong.

So report-builder returns an Azure azure-app-affinity cookie, the FE echoes it back as an X-RB-Affinity header per executionId, and the gateway forwards it upstream. The header rather than the cookie is what survives gateway scale-out.

MFP goes further with a shared, plan-keyed pin persisted on the scenario row, which outranks the per-browser token — so every user of the same plan converges on the one warm replica instead of each warming their own copy.

06 · The cache identity ruleThe single biggest defect family

This is the part to actually remember. The cache is keyed roughly report:{report_id} plus context — but what gets loaded into it depends on inputs that historically were not in the key. The next caller then silently reuses the wrong rows. Not an error, not an empty grid: plausible numbers that are wrong.

The rule. A cache key must include every input that narrows, filters or reshapes what is loaded. If two requests would populate the cache with different rows, they must not share a key.

Each of these has caused a real defect by being absent from the key:

  • Date window — the first warm loads today ± 3 weeks; a later caller wanting history silently reuses that narrow slice.
  • Execution filters — one execution warms with department=BIGBOYS; another reuses it.
  • Workflow stage / plan version — stage selection reads sharing one plan cache keyed only by org.
  • Fact source — an "already loaded" short-circuit returns before noticing the report now resolves to the lakehouse path mid-rollout.

Two corollaries. An already-warm short-circuit must re-validate the shaping inputs, not just return — "already loaded" is only true for the same window, filters and source. And a window derived from date.today() is computed once at warm time and goes stale while the cache stays resident, so either key on it or recompute it.

07 · RenderingHow tiles and cells diverge

KPI cards and grid cells come from the same warmed frame but not the same code path, and the separation is deliberate.

Coverage and serving never aggregate. Rolling up happens later, in the display cascade, which applies each metric's own aggregation. That is precisely what keeps ratio metrics correct — a margin percentage summed across rows is nonsense, so the layer that fetches rows is forbidden from summing anything.

Three sharp edges follow from that design:

  • Time grains must not be mixed in one rollup window — Q/H/Y suffixes belong to different forward windows.
  • A metric whose canonical aggregation the rollup engine cannot express must be rejected explicitly rather than routed in and quietly mis-aggregated.
  • There are row-oriented and column-oriented pivots. A field emitted through only one of them is simply missing from the other.

08 · EditingThe write path, briefly

/plan/edit applies an edit to the warmed frame, recomputes derived metrics, cascades to children, and eventually writes back. Three things are worth carrying around:

  • "Lock" means three unrelated things. held_nodes is a metric-dependency hold during roll-down; locked_field is the held factor in a product solve; plan_version.lockedBy is concurrency — which user may edit a scope. The source file itself carries a warning about the collision.
  • Write-back and publication must commit together. Committing one and failing the other leaves the two out of sync.
  • A self-guarded formula disables its own edit cascade. Metrics protect a seeded value with COALESCE(NULLIF("<self>", 0), <derivation>) so the warm-time formula sweep does not overwrite it — but the same string runs on edit, where the guard makes recompute a no-op. That shipped: editing Sales Units never moved Sales $. The fix is a separate unguarded cascade_formula for the edit graph.

09 · DebuggingReading a slow or wrong grid

  1. Wrong numbers, no error? Suspect cache identity first. Ask what shaped this load that is not in the key.
  2. Slow first open, fast after? That is the warm. Check cacheWarmedAt on /plan/state.
  3. Fast for you, slow for a colleague? Affinity — they landed on a different replica and warmed their own copy.
  4. Tiles disagree with the grid? The display cascade, not the fetch. Check per-metric aggregation and whether a ratio is being summed.
  5. Empty grid on a Completed execution? Snapshot rows are GC'd on a 30-day TTL. A reused old execution opens empty with no error.
