From file to grid

The retail data pipeline in fifteen steps.

A map, not a manual. Each step names what physically moves to the next one — because the handoffs are what the pipeline actually is, and they are the part that is hard to reconstruct from any single job's code.

Step 0

Before any data exists

  1. Register the feed config.source_definition says what the file is — its natural key, column contract, format, archive wrapper, and the detection rules that recognise it. config.cookbook says how to map it, as one row per transform step. → Nothing runs until these rows exist. No code is written to onboard a retailer.
Bronze

Getting it in

  1. File arrives Push (sftp, fe_upload) or pull (bigquery, fetched on a schedule). → a blob in ADLS under _unclassified/…
  2. Classify The feed's detection rules run in order; first match wins, no IO. → blob renamed to canonical data/…, plus a detected event
  3. Preprocess, if wrapped Unwrap zip / gz / tar.gz / xlsx. (xlsx counts as an archive — OOXML is a zip.) → inner files at canonical paths, one detected event each
  4. Write Header-validate, then stream the passing files in. → rows in bronze.raw_data — every column a string, each row carrying dataId = hash(uniqueCols)
Steps 1–4 coordinate through a log, not through calls. Every stage appends to config.pipeline_events; the dispatcher routes purely on state and holds no business logic; state_materializer projects the log onto config.pipeline_state, one row per file. This is why a stuck file is diagnosable — its entire history is a table.
Silver

Making it ours

  1. Cookbook transform Filter bronze.raw_data to the (orgId, sourceId) pairs this sink's cookbook configures, then run the transform chain. → MERGE on dataId into a typed silver table. This is where strings become dates, numbers and enums.
  2. Build structure Product hierarchy is derived: attributes → product_node_relation. Location hierarchy is declared: relations → location_closure. Two different models. → hierarchies become queryable at every level
  3. Apply mappings product_mapping / location_mapping. SAME pools two codes into one entity; SIMILAR borrows the other's demand as a proxy; REMOVE retires a prior declaration. → a style that changed code mid-season gets one continuous history instead of two truncated ones
  4. Aggregate agg_sales, agg_inventory. → weekly totals at PVL grain (product–variant–location)
Gold

Computing

  1. Facts gold.stock_facts_pvl — 13 columns, exactly one grain, no pooling. Raw variant and location; same-SKU grouping is deliberately deferred. → facts stay facts
  2. The cube gold.stock — 32 columns across six levels, built in phases: foundation → enrichment → rolldown → variant → ep_constraint → lost_sales. → every phase hands off through a Delta table, never in memory
  3. Forecast inference/demand fits the model. → writes demand back into gold.stock at its own levels
Serving

Getting it out

  1. Mirror targets/postgres copies 27 tables out of the lakehouse; targets/freshness maintains the source_last_updated ledger behind the product's "data has moved" surfaces. → Azure Postgres — an indexed, low-latency store the app can actually query
  2. Query Report widgets read Postgres through an ibis expression. Planning grids skip it and read the Delta files directly via DuckDB, warmed into a per-replica cache. → rows, in memory, on one replica
  3. Shape Rollup and the display cascade apply each metric's own aggregation. The fetch layer never aggregates — that separation is what keeps ratio metrics correct. → KPI tiles and grid cells
  4. Edit Plans only. /plan/edit → recompute derived metrics → cascade to children → write back. → back into the plan store, and eventually published
Running alongside all of it: ops/data_quality — five lanes checking silver and gold, the Postgres mirror, parity between the two, and the cookbook chains themselves. A passing run means "everything we could name was run, and everything we could not run is written down."

Three things this map makes obvious

  • Step 0 is the real work. Steps 1–4 are byte-identical for every customer. Onboarding a retailer means writing rows in two config tables, not writing a pipeline.
  • Step 5 is where typing happens. Everything upstream of it is strings. If a date parses wrong or a number arrives as text, the cookbook is where to look — nowhere else.
  • Step 12 is a boundary under renovation. The Postgres mirror is being decommissioned, which is exactly why step 13 has two different answers depending on which surface is asking.
