Source to screen

How a retailer's raw file becomes a number on a planning grid.

The platform is about ninety Databricks jobs arranged in layers, and almost none of the interesting behaviour lives in the job code. It lives in configuration tables — which feeds exist, how to parse them, how to map them, what the hierarchy is. Onboarding a retailer is mostly writing rows, not writing jobs. Understanding that inversion is most of understanding the platform.

Part oneThe journey

The layers, by job count:

sources/    1   postgres
bronze/    12   the ingestion chain
silver/    51   conformed dimensions and facts
gold/       8   stock, stock_facts_pvl, attribution, size_curve,
                lost_sale_events, weekly_sales_by_variant_location
inference/  1   demand
targets/    2   postgres (serving mirror), freshness (ledger)
ops/       14   data_quality, cost_attribution_meter, migration_executor, …

The shape is standard medallion — bronze raw, silver conformed, gold computed — with two additions worth noticing. Silver is enormous relative to everything else (51 of ~90 jobs), because conforming a retailer's idea of a product to ours is the actual work. And targets/ is a layer of its own: the lakehouse is not what the application reads.

Getting a file in

Files arrive one of two ways, declared per feed as sourceType: push (sftp, fe_upload) or pull (bigquery, fetched on a schedule by ingestion_pull_scheduler and ingestion_pull_connector).

Once a blob lands, six jobs move it, coordinated entirely through an event log:

JobDoes
ingestion_dispatcherStreaming orchestrator. Reads new config.pipeline_events rows and fans each out by state to one of three spawned jobs via jobs.run_now. Holds no business logic — no ADLS access, no classification.
ingestion_classifierApplies the feed's detection rules, renames the blob from _unclassified/… to a canonical data/… path, writes one detected or failed event.
ingestion_preprocessorDownloads archives and extracts inner files to canonical paths. Emits a detected event per inner file.
ingestion_writerHeader-validates, streams passing files into bronze.raw_data, writes a per-file manifest, emits a terminal state.
ingestion_mergerMerge handling for change-capture feeds.
ingestion_state_materializerProjects the append-only config.pipeline_events log onto config.pipeline_state — one row per originalEventId.
The design to take away. The chain is an append-only event log plus a materialised projection, not a set of jobs calling each other. pipeline_events is the history; pipeline_state is the current state per logical file, derived. The dispatcher is deliberately logic-free — it only routes on state. This is why a stuck file is diagnosable: the whole history of what happened to it is a table.

Bronze to silver

bronze.raw_data holds everything, all columns as strings. A silver job's entire structure is: filter bronze.raw_data to the (orgId, sourceId) pairs its cookbook configures, run the transform chain, write typed rows to its sink. The location_cluster job's README puts it plainly — the pipeline has "no table-specific logic — all mapping lives in the cookbook."

That is Part two. For now: silver jobs are thin because the mapping is data.

Silver to gold, and out

Gold computes: gold.stock (the demand pipeline, Part four), attribution, size_curve, lost_sale_events. inference/demand fits the forecast. Then targets/postgres mirrors 27 tables out of the lakehouse into Azure Postgres, and targets/freshness maintains a source_last_updated ledger that drives the "data has moved" surfaces in the product.

So which store does a screen actually read?

Four answers, and they coexist.

SurfaceReads fromVia
Control plane
config, executions, plan versions, locks		 Azure Postgres Always. Never the lakehouse.
Report widgets
/widget-data		 Azure Postgres — the 27-table mirror ibis expression through query-builder, executed on a pooled backend
Planning grids
/plan/data		 Databricks silver.mfp_facts DuckDB reading the Delta files directly by default; SQL warehouse as fallback
Demand-forecast grids Immutable Parquet tiles in Blob Warmed once cluster-wide, manifest coordinated in Postgres

The reason for the split is latency versus size. The Postgres mirror exists so ordinary report widgets get an indexed, low-latency, transactional store instead of a warehouse round trip. Planning grids skipped it because the MFP fact is large, is restructured per plan, and is edited — so it gets materialised into a per-replica DuckDB cache instead.

This is mid-migration, and it matters. The Postgres mirror is being decommissioned. targets/freshness exists specifically so the freshness surfaces survive that removal, and its README notes both writers run today — safe only because the ledger upsert is a monotonic GREATEST merge, so two writers observing the same batch converge in any order. If you are reasoning about where data comes from, check which side of that migration the table you care about is on.

Part twoOnboarding a retailer

Two configuration tables carry almost all of it: config.source_definition says what a feed is, and config.cookbook says how to turn it into a silver row.

The feed contract — config.source_definition

Sixteen columns. The load-bearing ones:

ColumnMeaning
labelShort feed name (sale, poupload). Explicitly "load-bearing, not cosmetic" — it is what a matching detection rule returns and what gets stamped on pipeline events.
uniqueColsOrdered source column names forming the feed's natural key. Their values hash into the per-row dataId, which is the key silver MERGEs on. The writer raises if it is unset.
schemaThe column contract, as a versioned envelope with a validationMode of shadow or enforce — so a new contract can be observed before it starts rejecting files.
detectionRulesOrdered rule chain, sorted by level, first match wins, no IO. This is how the classifier decides what an arriving file is.
format / formatOptionscsv / json / avro / parquet, plus reader options discriminated on their own format key. A row where the two disagree is rejected.
archiveFormatnone / zip / gz / tar.gz / tar.bz2 / xlsx — xlsx counts as a container because OOXML is a zip.
isActiveRead gate. Every bronze stage filters on it, so flipping it false retires a feed without deleting its config.

The cookbook — config.cookbook

A cookbook is not a file. It is a set of rows, one per transform step, keyed by (orgId, sourceId, sinkTable, transformGroup, transformOrder). Each row names a transformType from a closed set — direct, cast, column_map, string_replace, format_string, field_map, conditional, expression, constant, date_transform, split, aggregation, json_parse, … — and carries a JSON transformConfig validated against the Pydantic model registered for that type.

Three mechanics that explain most cookbook behaviour:

  • transformGroup 'base' is special-cased. It runs first against the raw frame. Every other group then runs against the base output independently, and the group results are outer-joined back on (orgId, id). That is how one feed populates several column families without them interfering.
  • transformOutput is a projection whitelist, not documentation. After a group finishes, the frame is cut to the union of every step's declared outputs plus the framework's passthrough columns. A column you computed but did not declare is dropped.
  • transformId is frozen at creation. Seeded once from the position, then never recomputed — so reordering a chain moves transformOrder and leaves identity alone.
The sharp edge. transformOrder is applied by sorting rows in Python after they are read, so the table's own row order is irrelevant — but a duplicate order within one group leaves the tie unresolved. Two steps at the same order is a non-deterministic cookbook.

Reconciling identifiers — the mapping tables

A cookbook parses one file. It cannot know that the retailer's SKU A-1123 is last season's A-1098 under a new code. That is a separate, customer-declared input: silver.product_mapping and silver.location_mapping.

Both carry the same three-valued relationshipType:

TypeProductLocation
SAMEThe two codes are one entity — pooled into a groupCollapse the two locations into one selling unit
SIMILARThe new side borrows the old side's demand as a proxyThe related location borrows the source location's demand
REMOVERetire this pair's prior declaration

product_mapping additionally carries a level of 'variant' or 'product' — whether the assertion is about two SKU codes or two product codes — and resolves both sides to surrogate ids while keeping the raw pair.

location_mapping does something worth copying: it keeps sourceLocationCode and relatedLocationCode verbatim as the customer wrote them, alongside the resolved ids, so the declaration "stays reportable and auditable against their location master". When a customer disputes a mapping you can show them their own codes, not our hashes.

The payoff lands in gold: gold.stock pools variants sharing a variant_group_member.groupId and pools SAME-mapped stores, so a style that changed code mid-season has one continuous demand history rather than two truncated ones.

Part threeThe entity model

Keys first

Every entity id in the platform is the same construction:

id = sha256( org's configured source columns joined by '|' )

A hash, not a UUID. Two consequences follow and both bite. First, the hash inputs are per-org cookbook configuration — a style/colour code for one retailer, an article number for another. Second, most orgs omit orgId from the hash inputs, so the value is unique only within an org and the real key is (orgId, id). Any join or uniqueness assumption on id alone is a latent cross-tenant bug.

The upside is that ids are reproducible: re-ingesting the same source row yields the same id without a lookup, which is what makes idempotent MERGE possible at this scale.

Product — hierarchy is derived from attributes

silver.product is deliberately thin: 9 columns, of which the interesting one is attributes — a JSON object whose key set is per-org and per-feed, with no fixed shape. silver.product_variant hangs off it with a variant JSON holding the distinguishing axes (size, colour, and org-specific ones like shape or material).

The hierarchy is not columns on the product. It is computed, across four tables:

TableRole
config.product_hierarchy_levelRegisters the org's levels as fieldIds
config.product_hierarchy_closureThe level ordering — root chain and depths
silver.product_hierarchy_nodeOne row per distinct node. attributes is the node's full path as JSON; id hashes that path
silver.product_node_relationPlaces each product at each depth — productId → nodeId, with nodeLevel and nodeDepth
The failure mode to internalise. product_node_relation decodes product.attributes as map<string,string> and looks up each registered hierarchy field id. A product whose attributes lack a registered field id yields no hierarchy node at that level. Not an error, not a NULL row — the product is simply absent from that level of every rollup. The contract "the org's registered hierarchy field ids must appear as keys in attributes" is enforced by the cookbook being written correctly, and by nothing else.

Location — hierarchy is declared as edges

silver.location carries 12 columns, with the same per-org attributes JSON, plus a few things promoted into real columns because they are queried: geo (a lat/long struct), countryCode, isActive, and typeId pointing at config.location_type — which is where isSelling lives, distinguishing a store from a DC.

Structure is expressed as edges, not attributes:

  • location_relation — parentId is the supplying side (warehouse, DC, store-owned box), childId the served store. These are supply edges, not geography.
  • location_closure — the transitive closure: ancestorId, descendantId, depth. Note the type column: two different edge sets share this table and are discriminated by it. Querying the closure without filtering type silently unions two unrelated graphs.
  • location_cluster — grouping for planning, with its own attributes.
The asymmetry is the insight. The product hierarchy is attribute-derived — nodes are computed by reading values out of a JSON blob. The location hierarchy is edge-declared — relations are stated, then a closure is built. They are modelled in genuinely different ways, so intuitions do not transfer. A product moves levels by its attributes changing; a location moves by an edge being rewritten.

Part fourGold stock

gold.stock is the demand pipeline behind replenishment and planning, and it is the highest-defect job family in the repo. Worth knowing why before touching it.

Why it needs its own job

Because it is not a view — it is a materialised multi-grain cube. Thirty-two columns, and a level discriminator deciding which dimension columns are populated on a given row: product_variant_location, product_variant, product, product_hierarchy, location, overall. Dimension columns are NULL at levels that do not carry them, and different producers write different levels — the forecast writes overall / location / product_hierarchy; the rolldown phases write the finer grains.

The metrics come in regime triples — full-price, markdown, and net:

sold      fpSold      mdSold      netSold
price     —           mdPrice     netPrice
cost      —           mdCost      netCost
inventory —           mdInventory netInventory
demand    fpDemand    mdDemand    netDemand

adjustedSold     — sold after stock-out censoring (full-price leg only)
adjustedDemand   — demand after the EP constraint is applied
lostSale         — sum of gold.lost_sale_events units, with reason codes

An org with no markdown feed has the markdown leg absent and net equal to the base — which is why so many of these columns read "a missing markdown leg counting as zero".

The v1 pipeline

PhaseDoes
1 · foundationinventory/sales, product availability, interpolation
2 · enrichmentadjusted sales, multi-level aggregates
4a/4b · rolldownproduct and product-location demand rolldown
5 · variantproduct-location demand → PVL via clamped historical proportions
6 · ep_constraintfan constraints out to PVL, distribute by largest remainder, aggregate back up in one MERGE
lost_salesaggregate gold.lost_sale_events per PVL/date onto gold.stock

All communication between phases goes through Delta tables — never an in-memory handoff. And no phase applies its own lookback or cap: a shared context builds the cutoff config, because a phase that re-derives its own window will disagree with the merge predicate.

PVL, and why v2 splits it out

PVL is product–variant–location, the finest grain in the system. gold.stock_facts_pvl is v2 Step 1, shipped and running alongside v1. Where gold.stock is 32 columns across six levels, stock_facts_pvl is 13 columns at exactly one grain — and its column comments state the design directly: variant is "raw variant grain; same-SKU grouping is deferred to rolldown", location likewise.

That is the whole point of the split. v1 pools SAME-mapped SKUs and stores at the foundation, before anything else happens. v2 keeps facts at raw grain and defers pooling downstream. Facts stay facts; the opinionated part moves later.

The other reason it is a separate table is a hard invariant:

A pipeline step must never write into a table it also listens to. Its own writes would re-trigger it. Each step writes to its own table — that is what keeps the change-propagation DAG acyclic, and it is exactly why stock_facts_pvl is separate from everything downstream.

Later v2 steps (stock_agg, stock_enriched, stock_demand, stock_v2) are designed but not built. Those tables do not exist; do not write code against them.

Where this pipeline actually breaks

Every one of these is a real review finding, and they generalise well beyond this codebase.

Pool arithmetic

  • An aggregate over a pool is not safe until you have decided what a non-positive total means. NULL, zero and negative are three different cases; collapsing them into one otherwise branch silently mis-allocates the entire pool.
  • Clamp pool aggregates at zero — one negative row can drive a sum ≤ 0 and set scaleFactor = 0 for the whole pool, not just that row.
  • Largest-remainder distribution needs a deterministic tie-break, or allocation is not reproducible run to run.

Join semantics decide whether rows vanish

  • An INNER join in a fan-out drops the unmatched side — so a WHEN MATCHED MERGE then leaves stale values in place, and removing a constraint appears to do nothing.
  • A LEFT join writes NULL for the unmatched side unless you coalesce back to the original.
  • An unconditional inner join against an optional dimension deletes data for every org that does not use it.

Borrowing must not carry the donor's grain

When a recipient borrows a donor's history, carry the recipient's productId and locationId. A donor with history at a location the recipient never trades at produces a phantom row there — and the left_anti replacement will not remove it, so it persists.

Ordering in CDF writers

Write facts before the watermark. A watermark MERGE that commits first leaves lastDataDate ahead of the data, and downstream reads an incomplete horizon as complete — which is the worst class of bug here, because nothing errors.

ClosingThe shape of it

If there is one thing to carry away from all four parts, it is this:

  • Behaviour is configuration. Feeds, parsing, mapping, hierarchy levels — all rows in config.*. Silver jobs are thin on purpose.
  • Identity is a hash, scoped by org. (orgId, id) is the key, always.
  • Product and location are modelled differently — derived from attributes versus declared as edges — and neither intuition transfers to the other.
  • The lakehouse is not what the app reads, except where it deliberately is, and that boundary is actively moving.
  • The dangerous failures here are silent: a missing attribute key, an INNER join, an unclamped pool, a watermark written early. None of them raise.
