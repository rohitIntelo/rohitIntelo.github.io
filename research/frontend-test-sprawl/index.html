Candidates

01

Collapse cell writability into one verdict

Strong in-process 20 test files → 2 suites
table/locks/{cellLock, nodeLocks, planningLock, planningRefusal, rolldownHolds}.ts · table/editing/{buildEditScope, metricRowScope}.ts · table/interaction/GridLockContext · dashboard/plan/planScopeWritability · hooks/report/usePlanLockWritability — assembled in useTableWidget.ts, useTableColumnDefs.tsx, EditableCell.tsx, TableWidget.tsx
Problem
Ten shallow modules in five directories each answer part of "can this cell be written, and why not". Each is tested with its inputs handed straight in, so the code that combines them in four call sites is never tested, and three shipped bugs sat in exactly that code.
Solution
One deep module takes the plan's state and a cell and returns {writable, reason}. The four call sites render that verdict instead of computing pieces of it.
Evidence
  • 08704405 RT1-4503: removing config.workflowStage "left all 26 tests passing".
  • 46b110a1 RT1-4505: TableWidget never supplied periodLock.nonEditableBuckets, and "the test that said otherwise built the field by hand".
  • dd207332 RT1-4070: metricRowScope was correct, but 3 callers never used it.
  • Planning lock is tested at 4 levels and pin at 3, but no test combines the levels.
locality: wiring bugs land in one module leverage: one verdict, four call sites interface is the test surface

Tests · 20 → 2 suites · 4 unchanged

  • Merge into the verdict suite (12 files): locks/__tests__/{drilledNodeEditLevel, nestedDerivedNodes, nodeLocks, planningLock, planningRefusal, rolldownHolds}, editing/__tests__/{buildEditScope, metricRowScope}, hooks/useTableWidget.cellLockedByOther, interaction/GridLockContext, dashboard/plan/planScopeWritability, hooks/report/usePlanLockWritability
  • Merge into a "locked cells render locked" suite that mounts TableWidget (8 files): useTableWidget.{lockTint, weekLock, planningLock, axisReadOnly, lockSiblingsWindow}, useTableColumnDefs.planningLock, EditableCell.{periodLock, readOnlyReason}
  • Survive unchanged: TableWidget.{planningLockDrill, lockMount}, useTableEditState.planningLock, drillDown/planningLevelDrill. planEditApi.periodLock moves to #2.
  • New: one wiring case per shipped bug:
    • The viewed stage, not the config stage, decides whether a compare cell is writable.
    • A closed week is read-only once TableWidget mounts with period locks.
    • A scope-gated cell refuses the edit on every path that can edit it.
  • Delete: none. Every case moves into one of the two suites.

Mocks that go:

Top recommendation

01 · Collapse cell writability into one verdict

It runs in-process, so it needs no new test infrastructure. It collapses 20 files into 2 suites. And three shipped bugs (RT1-4503, RT1-4505, RT1-4070) sat in exactly the wiring today's tests cannot see, so it shows the pattern pays off before any bigger investment.

Next: 02 · the plan backend seam. Its adapter is what #3, #5, #7 and #8 all build on.

Test layout convention · not a candidate

One co-located suite per module interface

  • Name the suite <Module>.test.tsx, next to the module it covers.
  • Scenarios become describe blocks, not filename suffixes like .lockTint. or .weekLock..
  • No __tests__/ directories. 162 files use them today, and the feature-root __tests__/ rule in conventions-typescript/SKILL.md:113 has already separated 17 tests from the source they cover (StoreCluster 8, UserManagement 6, Settings 3).
  • Shared test adapters go in two places:
    • src/test/ for adapters that cross features: the plan server, a provider-wrapped render.
    • <feature>/testing/ for builders private to one feature, such as makeWidget. The ESLint deep-import rule applies to tests too, so these must be imported relatively from inside the feature.

Main tradeoff: a deep module's suite gets long. useTableEditState.test.tsx already has 141 tests, and splitting by filename suffix was the release valve for that. This convention accepts longer files, navigated by describe, in exchange for fewer files. Fewer, larger files also shard less evenly across CI's 4 file-based shards.
