Trusting the numbers

How data quality is monitored across the lakehouse and its serving copy.

Most data-quality systems answer "is this table wrong?". This one is built around a harder question: "is there anything we failed to check, and would we know?" Nearly every design decision in it follows from refusing to let a check silently not run.

01 · ShapeFive lanes

ops/data_quality runs as a four-slot composite workflow — global, then databricks and postgres in parallel, then cross_lane — with a fifth cookbook lane validating the transform chains themselves.

LaneChecks
globalOrg-agnostic checks (org_id='*'). Cross-org collision detection and the surrogate-key lint. Aborts the workflow if config.active_orgs is empty rather than fanning out to nothing.
databricksDQX-driven Spark checks against silver and gold, fanned out per org.
postgresThe same checks against the Postgres serving copy, via SQL templates.
cross_laneCount, sum and sync-lag parity between Databricks and Postgres — does the mirror agree with its source?
cookbookValidates the transform chains in config.cookbook: static taxonomy checks plus data probes.

Results land in two Delta tables — ops.data_quality_runs and ops.data_quality_results — written by a MERGE keyed on (run_id, check_id), so a retried org worker is idempotent rather than duplicating rows.

02 · CoverageChecks are generated, not remembered

The most interesting decision in the job is that most checks are not hand-authored. The module that generates them states the reasoning in one line:

A hand-authored rule covers the table someone remembered.

So targets come from information_schema and an entity registry instead. Generated and hand-authored checks produce the same RuleFile object on the same code path, so nothing downstream knows the difference.

The generated families are gen_fk_*, gen_partial_key_*, gen_unique_* and xorg_collision_*. Hand-authored rules still exist for the domain-specific cases, as YAML: 

table: data-{env}.silver.cost_rate
checks:
- id: cbv_cost_rate_id_unique
  type: is_unique
  column: id
  impacted_services:
  - service: _unowned
    severity: critical
The registry gate runs first, and is allowed to fail the run. If the entity registry under-covers the catalog, generation would emit fewer checks than the data warrants — with nothing naming what was missed. That is described as "exactly the silent skip this job exists to reject", so an unregistered column propagates as an error instead of quietly shrinking coverage.

03 · ControlsPreventive and detective, in pairs

The clearest illustration of the design is a pair of checks on the same failure — surrogate key collision across tenants.

Recall how ids are built:

id = sha2(concat_ws('|', sourceColumns), 256)

If an org's sourceColumns omits an org discriminator, two tenants whose source systems emit the same natural key get the same id. An org-blind join then attaches the wrong tenant's row.

surrogate_org_lintcross_org_collision
TypePreventiveDetective
Readsconfig.cookbook — the generator configThe ids already written
FiresBefore the colliding row existsAfter it exists

Both live on the global lane, and the reason why is the sharp bit: the per-org lane cannot see this class of bug at all. The databricks lane filters orgId before every check, so is_unique on (orgId, id) passes by construction and a key spanning tenants is invisible. The module notes this was proven by seeding a collision into the local lane and confirming it went undetected.

Worth generalising. A check scoped the same way as your data cannot detect a violation of that scope. If every query filters by tenant, no per-tenant check will ever find a cross-tenant leak.

04 · The cookbook laneTesting logic that lives in a table

Because the transform logic of every Shape A silver job lives in config.cookbook rather than in job code, its test suite lives here rather than in the job packages — which carry registration tests only. Two tiers share one check engine.

Static tier — config-pure

Taxonomy checks over live config.cookbook rows, with hash-based change attribution so a finding names the chain, the check and the transformId that introduced it. Families that cannot run for a chain — no source_definition, no schema module — are "reported as inapplicable in the coverage record rather than silently skipped."

Probe tier — data-dependent

The Spark half, running self-consistent goldens incrementally off the change feed daily and full dimension-uniqueness scans on Sundays. Same contract: a probe that cannot run yields an error or inapplicable row, never an absent one.

The dimension-uniqueness probe is quietly clever:

For every parseable equi-join, the dimension must be unique on its join key at real data. For an equi-join against a unique key a left join cannot fan out, so this is also the join-explosion guard; an unparseable condition is reported as unverifiable rather than skipped.

One check, two guarantees — correctness of the dimension and absence of accidental fan-out. And an unparseable join condition is a reported state, not a gap.

How it is actually used

dbdev cookbook validate                        # whole corpus vs the committed snapshot
dbdev cookbook validate --sink sale --org 550b # one feed, full findings, exit 1 on error
dbdev cookbook pull && dbdev cookbook accept   # refresh snapshot + baseline
dbdev cookbook rules                           # regenerate probe rules
dbdev cookbook test                            # the CI ratchet suite, locally

pull + accept is required in any PR that changes cookbook rows — a freshness gate in pr-checks enforces it.

05 · FailureWhat "failed" actually means

This is the part that makes the job usable on a real codebase rather than permanently red.

The generated check families report the debt already in the data. Turned on naively, every run fails forever and the signal is worthless. So there is a ratchet: a run closes failed only on a finding absent from accepted_baseline.json. 

{"accepted": [
  {"lane": "databricks", "org_id": "<org>",
   "check_id": "gen_partial_key_silver_sale",
   "accepted_on": "2026-09-04",
   "reason": "why this is carried, not fixed"}
]}

Four properties of that file are worth copying wholesale:

  • An accepted finding is still written as fail with its count. Accepting changes the run's verdict, not the record. The debt stays measurable.
  • accepted_on and reason are required — enforced as a loader error, not a lint. You cannot accept something without dating and justifying it.
  • No run path writes the file. Accepting is a reviewed commit, never something a job does to itself.
  • Each run reports on the baseline itself: baseline_new for what fired, baseline_stale for an entry whose check now passes, and baseline_unresolvable for one naming a check that no longer exists.
That third bullet is the load-bearing one. A baseline a job can rewrite is a baseline that quietly absorbs every new failure. Making acceptance a human commit is what keeps the ratchet a ratchet.

Severity and routing

Severity is info < warn < error < critical, and it is a property of who is affected, not of the check. Each rule declares impacted_services, each with its own severity; the effective severity of a result row is the maximum across them. _unowned is the synthetic service for ops-only tables, routing to ops alone.

A week-1 policy caps everything at warn — applied at write time, deliberately, so that lifting the cap later does not retroactively change historical rows and break trend panels.

06 · TriageOrdering findings by cost

A validator that emits two hundred findings has just moved the problem. The triage module orders them "by what they cost, not what they are called", on two axes:

  • Certainty — damage happening deterministically on every row today outranks damage waiting on a bad input value. A NULL that is recomputable after a fix still outranks a latent defect, because the latent one has cost nothing yet.
  • Repairability — silent re-keying is permanent (a MERGE cannot un-duplicate), so latent identity corruption outranks latent batch failure, which is loud and leaves the data intact.

The second axis is the non-obvious one. It ranks a quiet problem above a loud one, because loudness is a form of safety: a job that crashes has not corrupted anything.

07 · ParityTwo lanes, one answer

The Databricks and Postgres lanes must agree, which is harder than it sounds. A worked example from the README, on is_in_set and NULL:

SQL three-valued logic means col NOT IN (…) treats NULL as passing. An interim revision "fixed" this on the Postgres lane by rewriting it so NULL counted as a violation — which made the same rule produce different counts on the two lanes. That was reverted. The current predicate is col IS NOT NULL AND col NOT IN (…), so NULL passes on both, matching DQX's default on the Databricks side.

The lesson is not about NULLs. When two engines implement the same rule, agreeing with each other beats either one being independently more correct — because parity checks compare their outputs, and a divergence shows up as a data problem that isn't one. The behaviour is now pinned by a test whose fixture has one NULL row and one genuinely out-of-set row, asserting a failing count of exactly 1.

ClosingOne principle, applied everywhere

Every part of this job is the same idea in a different costume:

  • Checks are generated from the catalog, because memory under-covers.
  • The registry gate fails the run rather than emitting fewer checks.
  • An inapplicable check is recorded as inapplicable, not omitted.
  • An unparseable join is reported as unverifiable, not skipped.
  • The global lane exists because a per-org check cannot see cross-org bugs.
  • The global lane aborts on an empty org list instead of passing vacuously.
  • Accepted findings are still written as failures, with a date and a reason.

A passing run here is not "we found nothing". It is "we ran everything we could name, and everything we could not run is written down". That is a meaningfully stronger claim, and it is the one worth building toward in any monitoring system.
